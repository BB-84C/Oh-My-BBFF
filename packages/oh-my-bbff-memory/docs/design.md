# Historical design archive — versions through 0.5.0

> Historical decisions and earlier implementation evidence only. This document is not the current runtime contract and is not packaged. Deployment-specific paths, old private API shapes, local parent walking and old native-budget scripts below are superseded by the current [README](../README.md), shipped JSON data and the public SDK. Do not use archived examples to infer current configuration/admission or to mutate a profile.

Status: **0.5.0 live** — read-only full-resident injection (M1), the memory
tool suite and the `update-memory` skill (M2), and the in-process Dreaming Resident (M3) are shipped and
active in the web profile. M3 scheduling, lease and stage/commit logic plus the plugin route are covered
by tests; the **first real model wake** remains the end-to-end acceptance step (§12). 0.4.0 adds
per-root-session memory toggles and the widget inventory/dream APIs (§13); 0.5.0 adds the approved
three-layer routed recall, global settings and per-session mode (§14). M4 is the panel.
Scope: a DSH-native memory system that mirrors the opencode structure we already run, without routed recall,
with an in-process Dreaming Resident that rewrites/archives memory instead of only appending.

## 3. Injection (M1)

Seam: `agent/pre-step` (same seam the shipped `dsh-agent-instructions` uses), injected as a persistent
user message whose source is producer-owned (format-v4 whitelist must be verified before M1 lands).

Render order, broad → specific (opencode precedence inverted: more specific later):

1. precedence header (direct user instruction > workspace memory > global memory > global AGENTS.md);
2. `Instructions from: $DSH_HOME/memory/<file>` for each global file, filename-sorted;
3. `Instructions from: <workspace>/.dsh/memory/<file>`, then compat dirs, each file once (sha1 of trimmed content dedupes);
4. every section is escaped for `</system-reminder>`.

Budget (`injectBudgetBytes`, default 559,662):
- render full text; if it does not fit, drop global files from the broad end first (workspace memory is more specific),
  emit a visible `[memory budget exceeded: omitted …]` marker and record a warning surfaced in the panel;
- the budget is a safety cap, not the design target — Dreaming rewrite/archival keeps the store inside it.

Reconciliation: per-file digest; a changed file replaces its prior section, a removed file emits a removal notice,
the same content never re-renders (identical to `dsh-agent-instructions` semantics, simpler implementation).
No per-turn re-injection of unchanged content.

## 4. Tools (M2)

Root sessions:

| Tool | Semantics |
|---|---|
| `memory_list` | list global + workspace memory files with size/mtime/sha1 |
| `memory_read` | read one file (scope + file name, no absolute paths from the model) |
| `memory_search` | substring + CJK bigram scoring over memory roots |
| `memory_write` | create/replace one file; **dry-run by default** returns the unified diff, `apply: true` performs it |
| `memory_delete` | delete one file; dry-run default, `apply: true` moves to `.archive` |
| `agentsmd_read` | read `$DSH_HOME/AGENTS.md` or `<workspace>/AGENTS.local.md` |
| `agentsmd_write` | dry-run diff + apply for global `AGENTS.md` / workspace `AGENTS.local.md` |

Subagents: `memory_list` / `memory_read` / `memory_search` (read-only) + `memory_candidate` which writes a
proposal into `$DSH_HOME/memory/.candidates/<session>/` for the root agent or the resident to fold in.

Skill `update-memory` is a faithful port of the opencode skill: two-stage scope→shape routing, traceable evidence,
duplication/contradiction/style checks, explicit `Apply?` confirmation, forbidden wholesale rewrite for the
working agent (Dreaming is the only writer allowed to rewrite).

## 5. Dreaming Resident (M3)

Lifecycle (all inside the host plugin, activated/disposed with the profile):

1. every 60 s (plus a ~3 s boot check): if `now - lastWakeAt >= 6h`, try to take the machine lease; on
   success wake;
2. wake = create the resident session on the first wake (`ctx.agents.create`) or resume it
   (`ctx.agents.resume`) — title `BBFF Dreaming Resident 🌙`, workspace `$DSH_HOME/dreaming/` — and send
   it a wake prompt containing: the new session/user-text manifest since checkpoint, current memory
   inventory (paths, sizes), budget usage, and the review contract;
3. resident works with `dream_*` tools:
   `dream_delta` (paged user-text increments, never tool output), `dream_read` (memory files),
   `dream_stage` (replace file / remove file / archive, each with reason + evidence), `dream_discard`,
   `dream_commit` (apply stage atomically), `dream_status`;
4. commit: snapshot touched files to `.history/<ts>/`, write `.dreaming/stage` → live, move deleted files
   to `.archive/<date>/`, append `changelog.jsonl`, update checkpoint + `lastWakeAt`;
5. dispose: release lease, stop the timers, dispose the resident agent handle.

Wake contract (resident prompt): "This is a 6-hour review. Writing nothing is a valid outcome. You may
carry an observation across wakes; only repeated evidence justifies a new memory. You may rewrite, merge,
split, or archive existing memory when it is stale, duplicated, or contradicted. Every write must state
evidence."

Multi-process: the lease is the only guard. If every DSH process is closed, dreaming pauses; the next
start sees the overdue `lastWakeAt` and wakes immediately (D16/2).

Resident session identity: one persistent session (so observation history survives), created
programmatically on the first wake and resumed on later wakes; its id is persisted in
`.dreaming/state.json` (`residentSessionId`).

Creation/composition seam (verified against the installed `@deepseek-ai/dsh-agent` /
`dsh-agent-preset-registry` / `dsh-system-prompt` / `dsh-tools` type declarations): inside the
`agents.create`/`agents.resume` setup callback the plugin calls
`agentPresets.resolve()` (async) + `agentPresets.mount(agentCtx, id)`, registers persona/context through
`systemPrompt.section()/context()`, and calls the agent-scoped `tools.restrict({allow: dream_*})`. A
restriction filters what the scope *inherits* (global + ancestor, including preset-mounted tools), so the
resident cannot see the working-agent tool set. If the restriction cannot be applied the resident refuses
to start rather than run with full tools. If the preset mount fails it is recorded as a warning and the
resident runs with the deployment composition (degraded, never tool-broad).

**M3 limitation (not proven by tests):** no test triggers a real wake, so "the model turn runs and calls
`dream_commit`" is unverified until the first real wake (after the 6 h interval, or via
`?dream=wake&run=1`). Everything up to prompt delivery is covered; see §12.

## 10. M1 implementation notes

- Tests: `.tmp-llm-test/test-bbff-memory.mjs` (32 checks: discovery/dedupe/order/render/escape/budget/

## 9. Web-app preset override (M0 detail)

`dsh-web-app` disables the top-level `agent-instructions` row (its `cordis.patch.yml` line ~573) and declares the
row inside each agent preset under `presets/*.patch.yml`. A profile patch cannot reach a nested preset entry, so a
Cordis patch can only replace the whole preset declaration. `scripts/patch-profile-budget.mjs`:

- reads the shipped `presets/cordis.patch.yml` and `presets/standard.patch.yml`;
- copies each `preset-*` declaration into the profile patch as an id override, changing `maxBytes: 65536` to
  `262144`;
- keeps the generated block between `# >>> oh-my-bbff-memory:preset-budget` markers so re-runs replace it.

Cost: the generated block freezes the shipped preset declaration at the current DSH version — re-run the script
after every DSH upgrade. `preset-ptc` / `preset-minimal` are left at their defaults (only used when a session
explicitly selects them). Verified with `dsh --profile web --dump-config`: `preset-cordis` and `preset-standard`
now show `maxBytes: 262144`.

## 12. M3 implementation notes

- Package `oh-my-bbff-memory@0.3.0`. New modules: `lib/dream-tools.js` (the seven `dream_*` tools) and
  `lib/dreaming/{state,lease,changes,sessions,kernel,resident}.js`. `package.json` `files` covers `lib/`
  so the packed tarball carries all of them (13 files total).
- `index.js` wires M3 after the M2 tools: kernel over `$DSH_HOME/memory/.dreaming`, session source over
  `ctx.get('sessionQuery')` / `ctx.get('sessionPersistence')`, resident, dream tool registration, the
  `?dream=status|wake` route action, and the resident lifecycle through `ctx.effect` dispose.
- `export const inject` stays `['workingDirectory','webServer','tools']` and is mirrored in
  `cordis.patch.yml`. The resident's own services (`agents`, `agentPresets`, `sessionQuery`,
  `sessionPersistence`, `agentDefaultModel`, `sessionTitle`, `systemPrompt`) are read through `ctx.get()`
  and are deliberately **not** injected: a required Cordis inject is a load gate, so a composition
  without one of them would lose M1 injection and the M2 tools entirely. A missing resident service
  degrades the resident (wake refused / `errors[]` entry), not the plugin. The `web` profile supplies
  all of them.
- First-install safety is a state invariant, not a hope: a missing `state.json` is written with
  `bootstrapped: true` and `lastWakeAt = activation time`, so there is no wake for 6 h; an *existing*
  state with an old `lastWakeAt` still wake immediately (boot catch-up). Install verification reads
  `.dreaming/state.json` and asserts no `residentSessionId` / `activeRun`.
- `?dream=wake` without `run=1` is a dry run: it reports the decision and proves the lease can be taken
  (then releases it) without creating a session or spending a model call. `?dream=wake&run=1` is the real
  path and still obeys the clock, so immediately after installation it answers `interval-not-elapsed`.
- Delta selection reads only genuine human `user/message` text: `source.kind === 'user'`, subagent-origin
  sessions excluded, resident workspace/current resident session excluded, and non-user producer kinds
  (including the M1 memory baseline `plugin:bbff-memory`) never enter the delta. Scans are bounded; an
  unvisited session keeps its cursor for the next delta, so truncation never silently skips input.
- Controls (M3): `dream_stage` validates plain `*.md` names (no directories/traversal), requires reason +
  evidence, caps content at 512 KiB, and keeps one op per target file; `dream_commit` recomputes each
  target from its recorded scope root (a tampered manifest cannot redirect a write), snapshots existing
  files to `.history/<ts>/<scope>/`, writes via temp+rename, archives removals to
  `.archive/<date>/<scope>/`, appends `changelog.jsonl`, and closes the run. A commit with nothing staged
  is a valid outcome and still closes the review.
- Route lifecycle gotcha found during the 0.3.0 install: `webServer.register()` returns a disposer but does
  not bind the route to the calling fiber, so the M1/M2 versions left their handler at
  `/oh-my-bbff-memory/api` after HMR replaced the plugin and the next activation failed with
  `duplicate exact route` (the old handler kept serving, without the `dream` summary). Fix: the plugin now
  registers its route disposer with `ctx.effect` so every future unload releases it, and — one-time
  upgrade recovery — when registration collides it reclaims exactly that documented path from the
  `webServer` route table (warning logged). Verified live: the installed 0.3.0 handler serves the `dream`
  summary and `?dream=status|wake`; a fresh profile never needs the recovery path.
- Tests: `.tmp-llm-test/test-bbff-memory-dream.mjs` — 193 checks over an isolated `mkdtemp` `DSH_HOME`,
  never calling a model: state math (first install / interval / boot catch-up / corruption tolerance),
  lease (acquire, refusal, staleness takeover, heartbeat, release, corrupt-file recovery), stage/commit
  (validation, history, archive, changelog, checkpoint advance, workspace scope), synthetic-session delta
  and paging, the seven-tool registration + parameter validation + stage→commit cycle, the resident prompt
  contract, and the plugin route (including the `run=1`-while-not-due refusal and stale-route reclaim).
  M1 (32 checks) and M2 (25 checks) still pass.
- **Unproven:** the real wake (a model turn that calls `dream_commit`) and the live multi-process lease
  race. The creation seam was verified against the installed type declarations, not by running a wake.
  First real wake is expected 6 h after installation, or on demand with `?dream=wake&run=1`.

## 13. 0.4.0 implementation notes — per-root-session toggles & widget API

- Package `oh-my-bbff-memory@0.4.0`. New modules: `lib/toggles.js` (persistence + key/format helpers) and
  `lib/root-session.js` (parentSession chain resolver). `index.js` grows: toggle filtering in `compose`,
  `buildInventory`, `toggleAction`, the inventory/toggle route branches, and the widget dream contract.
- Persistence: `$DSH_HOME/oh-my-bbff-memory/toggles.json` `{version:1, sessions:{<rootSessionId>:{disabled:[...]}}}`
  — only disabled `scope:file` keys are stored; the file is written atomically (temp+rename), read on every
  compose/inventory so a widget change is picked up immediately, and corrupt/missing content degrades to
  "all active". Toggle writes inside one process are serialized so overlapping POSTs cannot lose a change.
- Root resolution: header `parentSession` walk with three header sources in cost order (live
  `ctx.agents.get`, `sessionPersistence.stat`, `sessionQuery.readSession`), depth bound 64, cycle guard.
  Total function: unknown session / broken chain / cycle / missing service all fall back to the session's
  own id and never throw. Subagent headers are written by `dsh-subagent` with `parentSession =
  parent.session.header.id` (the team plugin reads the same field), so inheritance is automatic.
- Injection: `compose()` scans, resolves the root, filters disabled files, then runs the unchanged
  digests/render path. A toggle change therefore appears on the next pre-step of every affected session as
  the existing removal/`Additional memory` update message; re-enabling restores it. Budget semantics are
  untouched. Known limitation (inherited from M1): a session resumed after a process restart adopts its
  visible baseline, so toggles changed while the process was down are not retro-notified.
- Inventory/toggle API: `GET ?inventory=1&sessionId=` and `POST {action:'memory-toggle'}` as documented in
  README §0.4.0. Validation is against the *current* inventory (unknown key / invalid scope / non-toggleable
  instruction file / non-boolean enabled → 400 `{ok:false,error}`); the write targets the resolved root
  session even when a child session id is supplied; the response returns the refreshed inventory.
- Instruction files: `dsh-agent-instructions` has no per-session disable API (only row config:
  `maxBytes`, candidates); per-session AGENTS.md toggling would require forking that plugin, so the
  inventory reports `toggleable:false` with that reason, plus `path`/`exists`/`bytes` for the widget.
- Dream status contract: `?dream=status` returns exactly `{ok:true, dream:{enabled, due, nextDueAt,
  lastWakeAt, wakeCount, residentSessionId, activeRun:{runId,startedAt,kind}|null, lease:{pid,host,
  heartbeatAt}|null, stagingCount}, decision, lastResult}`. Built from `kernel.statusSync` (added so the
  plain GET stays synchronous); read-only, no wake, no session creation. The plain status route keeps its
  `dream` summary (contract fields + `wakeIntervalHours` + `lastResult`).
- Tests: `.tmp-llm-test/test-bbff-memory-toggles.mjs` — 100 checks, isolated `mkdtemp` `DSH_HOME`, no model
  call: toggle store round-trip/persistence/corruption/key validation, root-chain resolution and fallbacks,
  root and child injection filtering with next-pre-step reconciliation and re-enable, toggle-through-child
  writing the root entry, second-instance store scoping, inventory/API shapes and 400s, dream contract
  (including activeRun/stagingCount from a staged dream op). M1 (32), M2 (25) and M3 (193) checks still pass.
- **Unproven:** the live widget click path (the widget lane ships in parallel; a page refresh is the user's
  step) and browser-driven toggle timing; everything else above is covered by the isolated suite.


## 14. Routed recall — approved, implemented in 0.5.0

Status: **implemented** (`oh-my-bbff-memory@0.5.0`) per the owner ruling. Full-resident (D2) stays the
default mode; routed mode is the approved three-layer alternative. Owner adjustments applied: resident
layer contains ONLY the natively loaded `AGENTS.md` / `AGENTS.local.md`; no memory file is hardcoded
resident (the `xx-abc-xyz.md` naming is our convention, not a product assumption); disabled files take
part in neither routing nor retrieval; new sessions default `full`; window (3 user turns), top-K (2) and
the L2 byte budget (120 KB/turn) are global settings.

### Motivation

Full-resident injects every global + workspace memory file on every request: 430,509 B memory plus the
natively loaded 193,933 B AGENTS.md, about 160k+ tokens per request. Routed recall keeps the same
reachability while making most of that cost conditional: a small router index is resident, matched files
are injected per turn, and everything else stays available through the existing read/search tools.

### Three layers (implemented)

- **L1 — resident**: only the natively loaded `AGENTS.md` / `AGENTS.local.md` (routing them would require
  forking `dsh-agent-instructions`, which has no per-session API). In routed mode the plugin additionally
  injects the generated **memory router index**: one line per active file with its `key` (`scope:file`),
  frontmatter `name`/`description`, top-level (`# `) headings and size. The index is router metadata, not a
  memory file, and no file name pattern is assumed.
- **L2 — trigger layer (per turn, deterministic)**: score the last N genuine user turns (default 3)
  against index metadata — frontmatter name (weight 3), description (2), top-level headings (2), filename
  tokens (1.5); English words are lowercased/destopworded and Chinese contributes CJK bigrams; idf is
  computed over the active index. Inject the top-K full files (default 2, byte budget 122880) under a
  visible `[routed: <key>, score=<n>, why=<field:token …>]` marker. Files already injected with the same
  content are skipped, so a repeated match does not re-spend context. No match injects one hint line
  pointing at the tools (once per session). No extra model call; recomputed on every pre-step and
  reconciled through the existing injected-state diff.
- **L3 — on-demand**: every non-injected file stays reachable via `memory_read` / `memory_search`.
  Disabled files are excluded from the index, the router AND retrieval: `memory_read` returns no content
  (`disabled: true`), `memory_search` skips them, `memory_list` marks them.

### Switch semantics (implemented)

- The BBFF settings menu (same place as notes) sets the global `defaultMode` (`full`|`routed`) and the
  route knobs in `$DSH_HOME/oh-my-bbff-memory/settings.json`: `routeWindowTurns` (1-20, default 3),
  `routeTopK` (1-10, default 2), `routeMaxBytes` (16384-524288, default 122880). Missing/corrupt file
  means defaults; POST validation is strict (400 on invalid).
- Effective mode = per-root-session override (persisted in `toggles.json` sessions entry as `mode`) >
  global `defaultMode`. Overrides are inherited by subagents through the root chain; `default` clears the
  override.
- Effective on the next pre-step: full -> routed reports the previously injected files as `Memory removed`
  and installs the router index as a replacement baseline; routed -> full emits one replacement full
  baseline.
- API: `GET ?settings=1`, `POST {action:'memory-settings'}`, `POST {action:'memory-mode'}`; the inventory
  gains `mode`, `modeSource` and a `settings` summary; `GET ?route=preview&sessionId=` exposes the current
  routing decision (window messages, index, scores/why, budget) read-only for debugging.

### Resolved open decisions

1. Trigger mechanism: **hybrid** — deterministic L2 auto-injection + index + tools (approved).
2. New-session default mode: **full** (owner decision, temporary).
3. `00-*`-style files: **not resident**; no file is hardcoded (owner: the format is our convention, and
   other users will not follow it).
4. Routing window: **last 3 user turns**, configurable in settings.
5. L2 budget: **top-2 files, <=120 KB per turn**, configurable in settings.
6. `AGENTS.md` / `AGENTS.local.md`: **native-only, out of routing scope** (would require forking the
   native plugin).

### Tests / limits (0.5.0)

`test-bbff-memory-routed.mjs` (129 checks, isolated `mkdtemp` `DSH_HOME`, no model call) covers settings,
mode override, arbitrary-name index generation, English/CJK scoring, window/top-K/budget/no-match,
full<->routed reconciliation, subagent inheritance, disabled exclusion (index/router/preview/tools) and
the API shapes. Not proven: a live model turn driven through the router; the widget settings panel; the
behavior after a process restart adopts the visible baseline and only routes new matches from then on.
